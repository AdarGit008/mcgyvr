# Session — lane/129 — 2026-08-03

## Did

Measured all three counts over the corpus #125 pinned, and registered them as
CLM-0007, CLM-0008 and CLM-0009 with vendored citations. The headline is that
**the reach gap is small** — smaller than the figures the inherited ADRs quote
without citation — and that two of the three counts are worth as much for what
they rule out as for what they measure.

**Count 1 — reach. 633 of 5,671 executable added lines were never executed:
11.2%, about 9 lines per accepted change.** Per frame, which is how it has to be
read: mcgyvr 13.1% (n=20, coverage **imposed**, and 81% of the corpus by line),
click 7.0% (n=30, declared), immer 3.8% (n=17 of 27, declared). Dropping mcgyvr
leaves 4.7%. If #123's rung is justified on reach, it is being justified on
single digits, not on ADR-0004's 20–40% or ADR-0008's ~60% — both of which
CLM-0005 had already put in question, and neither of which this supports.

The measurement runs the suite **77 times, at each change's own commit**, rather
than once per frame. A line number only means something in the tree that
contains it, and mapping old numbers forward would put a tracking heuristic
between the corpus and the number. The frames turned out cheap enough (~13s per
commit) that the faithful version was affordable, so there was no trade to make.

The classification is **four-way, not two** — reached, unreached,
non-executable, not-reported — and that choice carries the result. 8,521 added
lines, **60% of what was measured**, are blank, comment or docstring and were
never going to execute. Reporting the gap as `added − reached` yields "64% of
added lines are never executed", which is true, quotable, and five times wrong
as a size for #123. `tests/test_reach_counts.py` pins the four buckets to
partition the added lines exactly, so that arithmetic stays available.

**Count 2 — absence is 0 of 77 commits and 0 of 3 repositories, and this corpus
cannot answer the question it was asked.** The frames are one mature repository
per launch language, so every one declared a check before a single commit was
enumerated. The zero is exact and structurally uninformative, and the finding is
the negative one: **#123 must not be argued from it**, and sizing the
"nothing declared" branch — where a contract needing acceptance commands is
rejected at load, making those task types unreachable rather than weakly checked
— needs a different corpus and a different issue. What the count did earn is a
cross-check: it re-derives each frame's declaration from every commit's tree
independently, and agrees with the `declared_check` #125 wrote by hand.

**Count 3 — 0 false positives on 358 resolved call chains on added lines**
across the 50 Python-frame changes. That is an upper bound, not a demonstration
of zero: by the rule of three the true rate is under ~0.8% at 95% confidence.
The useful part is off the added lines. Widened to all 5,002 chains in the
touched files, ghostcall produced 7 verdicts at **4 distinct sites, every one of
them platform-conditional code that is correct on the platform it guards** —
`os.startfile` twice, `sys.stdout/stderr._original_fd` (click's own runtime test
shim), plus `msvcrt` as the single unimportable root. The mechanism is inherent
rather than incidental: `check()` resolves by importing and introspecting the
**live** interpreter, so a correctly-guarded foreign-platform API is
indistinguishable from an invented one. A rung adopting this resolver inherits
that, and the mitigation is a design property — the container's platform, and
whether guarded branches are excluded — not something the tool can fix. That is
a more actionable answer for "blocks or reports" than the bare zero would have
been.

**Three rig defects were found and fixed before any figure above was taken**,
and they are written into the measurements README because a measurement that hid
them would be worth less than none:

1. `uv`'s rayon pool could not spawn threads under a 1024-PID container ceiling,
   silently losing 7 of mcgyvr's 20 changes — a rig failure wearing a target
   failure's clothes.
2. vitest writes through `--coverage.reportsDirectory`, which persisted between
   commits, so a run that produced no coverage **copied the previous commit's
   report through**. Ten immer rows were another commit's data. This is the same
   shape as the defect that voided the local-ai clean run, which is why it was
   worth chasing a suspicious timing down.
3. Count 3 reported a whole-file flag total while recording only the flags on
   added lines, asking the reader to take seven verdicts on trust. Recording all
   of them is what surfaced the platform-conditional finding.

**A finding about the corpus, not just the counts.** Chasing (2) turned up that
**a frame's declared check is not constant over its history**: at 10 of immer's
27 commits `scripts.coverage` is `jest --coverage`, predating the vitest
migration. `corpus.json` pins one `declared_check` per frame read at the tip, so
for those commits the tip's command is anachronistic — ADR-0006's substitution
arriving through time rather than through a detector. They are excluded and
listed with their reason (80 added lines, 0.6% of the corpus) rather than
measured with a command the repository never declared then, and every row now
carries `declared_coverage_at_commit` so this is visible in the data.

Coverage of the pinned denominator is **67 of 77 changes and 14,192 of 14,272
added source lines (99.4%)**. The rig recomputes each change's added *lines*
(the corpus pins only their count) and refuses to run when its total disagrees,
so the numerators cannot drift from the denominator unnoticed. Reproducibility
is demonstrated rather than asserted: two independent runs returned identical
per-commit figures for every mcgyvr change.
