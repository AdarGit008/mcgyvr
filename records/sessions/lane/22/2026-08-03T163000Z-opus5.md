# Session — lane/22 — 2026-08-03

## Did

Built #22: per-source liveness, in `src/mcgyvr/availability.py`, entering the
ladder through a two-method seam on `pool.source_map`.

**The problem is cost, not detection.** Finding out that a host is not answering
is easy. Finding it out *once* is the work — a ladder escalates, so a dead source
discovered at dispatch time is discovered again at every attempt, and three rungs
on one dead host is three connect timeouts for one fact. So a verdict is cached
for the life of an `Availability` (one per run, no expiry — a run is short, and
missing a source that recovers mid-run beats a re-probe storm at every
escalation), a batch is probed concurrently, and the probe timeout is 2s where
`runner.GENERATE_TIMEOUT_S` is 120. Those two measure different things: a local
7B taking ninety seconds to answer a capped generation is healthy; a host taking
ninety seconds to accept a TCP connection is not. A test holds the ratio.

**A probe is a question about the source, never a generation.** It reads the
protocol's model-list path — free, immediate, side-effect-free. Sending a real
completion to test liveness would cost tokens and seconds and would conflate two
failures a caller has to tell apart: a host that is down, and a model that is not
loaded. Model presence is already `detect.Backend.has_model`'s question.

**The classification is where the thinking went, and it turns on one
observation: any HTTP answer proves something is listening, so the real question
is whether a *dispatch* would work.**

- transport failure (refused, DNS, timeout) → **down**
- 401 / 403 → **down**, and this is the case a naive check gets wrong: the source
  *is* answering, so "did it respond" would call it live and hand every rung on
  it to a dispatch that fails identically. The reason names the variable and
  never quotes its value.
- 5xx → **down**; it is there and telling us it cannot serve
- **404 / 405 → live.** The classification most likely to look like a bug, and
  the one that matters most. The model-list path is optional — an
  OpenAI-compatible server may serve `/v1/chat/completions` and 404 at
  `/v1/models`. Reading that as down would skip a *working* source: a false
  negative that silently shortens the ladder, strictly worse than the wasted
  attempt it was trying to save. Verified end to end against a real server, not
  only in a stub.

**The seam is deliberately narrow.** `source_map(config, probe=None)` still
touches no network by default; reachability enters through `SourceProbe`, a
structural type whose whole surface is `unavailable(endpoints) -> {source:
reason}`. So `pool.py` learns nothing about HTTP, timeouts, caching or retries,
and nothing above the seam gains a way to learn where a rung runs. Unreachable
sources' rungs become ordinary `Skipped` entries carrying the probe's own words,
rebuilt in declared ladder order so the structurally-skipped and the unreachable
interleave as the config reads rather than arriving in two blocks.

Two things the tests caught that I had wrong:

- `source_map` was handing the probe one endpoint **per rung**, so a source
  serving four rungs arrived four times. `Availability` deduplicates internally,
  so the behaviour was right — but that made correctness depend on the
  implementation deduplicating for us. Fixed on the caller's side of the seam:
  it now asks about distinct sources only.
- `test_pool.py`'s architectural guard on who may import `Endpoint` fired, which
  is exactly what it is for. `availability.py` was added to `BELOW_THE_SEAM`
  **with the argument written into the comment** — it does what a runner does,
  takes an endpoint and sends it a request — rather than being quietly appended.

Verified live: three rungs across two dead sources resolve in **2.2s**, not 6,
each carrying its own reason, exit 0. `mcgyvr pool --probe` reports every source
that was asked, live ones included — a ladder that came back intact is only
reassuring if you can see the question was actually put.

#23 (capacity semaphore) is the other E3 child that acquires at this same seam,
and `Endpoint.max_parallel` is already carried for it. #24's escalation is the
thing that makes this lane's caching pay, and is where a "source recovered
mid-run" policy would belong if one is ever wanted.

Two decisions worth re-opening deliberately rather than by accident:

- **The cache never expires.** Correct for a short run and wrong for a long one.
  If the orchestrator grows a long-lived process, this becomes a stale-verdict
  bug rather than a design choice, and the fix is a TTL, not a wider cache.
- **A probe is not retried.** One probe, one verdict, one run. A source that
  blips during the probe window loses its rungs for that run. That is the right
  trade at this timeout — a retry doubles the worst case, which is the cost this
  whole module exists to bound — but it is a trade, not a free choice.
