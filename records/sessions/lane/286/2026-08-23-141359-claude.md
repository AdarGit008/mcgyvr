# Session — lane/286 — 2026-08-23 (twenty-fourth)

## The ruling

The run contract's second post-state clause read **"no container of ours"** and
the reading beneath it was `docker ps`, which lists **running** containers only.
Two ways out were put to the owner: widen the check to `docker ps -a`, or narrow
the clause to "running" with its reason stated. **The owner chose to narrow.**

The reason, written into `docs/run-contract-2026-08-22.md` §4 as a dated
correction: a stopped container holds nothing this rule protects — no card, no
port, no process, and no claim on the next cell, which removes it before it
launches. Requiring its absence would make the contract's cheapest guarantee
turn on a state that costs nothing to leave behind.

**The original sentence is left byte-identical.** A pointer sits beside it and
the correction carries the change, which is ADR-0039's form. The one departure
from that form is the pointer itself: an ADR's superseded figure is harmless
because the *code* is operative, whereas §4's four clauses in check order are a
list an operator acts on directly, so a reader who stops at the list must not be
left acting on the superseded one.

## What landed

`50e69c3e`, then the corrections below.

- **The record takes `-a`** (`vllm.py:475`), so an exited container appears with
  its status and the `docker inspect` that follows recovers the argv it died on.
- **The gate does not** (`vllm.py:570`). `released` decides whether anything of
  ours still holds the card, and a stopped container holds none of it. **The
  record sees more than the gate acts on, and that asymmetry is the answer
  rather than a leftover.**
- **The other two `docker ps` reads keep their running-only form, and one of
  them matters.** `launched_width` reads `--max-num-seqs` off a container's own
  argv, and `docker ps -a` lists newest first — a sweep that added `-a`
  everywhere would answer with the width of the run that **failed**. That is a
  mutant in the sweep below, and it is killed.
- **A failed cell's container is removed at once, because its reason is read
  first.** `_launch_log` (`vllm.py:1109`) reads the engine's last 40 lines on
  the failure path and carries them, scrubbed, into the refusal. Keeping the
  container until somebody looks makes every launch depend on a human having
  been there, and a campaign runs unattended for hours.
- **The pip rig lost the reason the same way and nobody had noticed.** The
  refusal named two places to look; the container rig destroys its one with
  `docker rm -f`, and the pip rig redirects `> /tmp/vllm-serving.log`, which
  **truncates** the previous cell's rather than appending to it. Both launchers
  are read now.

## Session 24, continued — #353, the third term, measured on one engine

**#353 is answered, and the two engines answer differently.** The route the
issue ranked first works on vLLM and does not exist on ollama, and both halves
are measurements rather than inferences. Evidence:
`records/evidence/2026-08-23-sole-client-counters/README.md`.

**vLLM: `vllm:request_success_total`, summed over `finished_reason`.** Five
`/v1/completions` moved it by exactly five. Nothing else moved it at all —
`/health`, `/metrics`, `/ping` and `/v1/models` by zero each, three kinds of
failed request by zero each, and **two full `observed.capture()` passes by zero
each** while moving `http_requests_total` by exactly seven each. So **the
reading does not perturb the counter it reads**, and the arithmetic needs no
correction term for the harness's own traffic. That last control is the one
that makes the route usable rather than merely plausible.

A request that failed at the API layer is not counted, and that is **correct
for this question rather than a shortfall**: a request that never reached the
engine never entered a batch, so it cannot have changed the batch shape a
re-run has to reproduce. `http_requests_total` catches those and is kept beside
it as a constant for the refusal to cite.

**ollama: no counter, and the engine says so itself.** ollama answers 404 on
`/metrics`; its `llama-server` child answers **501** naming the flag that would
enable it — `Start it with --metrics` — and the child's own `/props` reports
`endpoint_metrics: false`. ollama spawns that child and does not pass the flag.
The refusal records that, which is a fact about reach, like `concurrency`'s was.

**`/slots` `id_task` was the other candidate and is refuted.** It is monotonic,
so it looked like a counter. Its increment per request is neither 1 nor stable
— **5.00, 7.00, 7.00, 5.67 measured on one server, one model, one request
shape**. llama.cpp assigns task ids to internal work too, and how much internal
work a request causes depends on cache state. It can say the server did
something; it cannot say how many requests that was, and a count is what the
subtraction needs.

**What is recorded, and what deliberately is not.** The field is
`server_completions_in_window` — named for what it holds, never for the verdict.
It carries the delta, both edges, the counter name and the window. **The
subtraction is not done here**: foreign traffic is that value minus the rows
this run dispatched, the dispatched-row count is a property of the runner, and
passing it would touch both runner call sites, which are SURFACE. It is in
`run.json` beside the file, so a reader has both terms and the note spells out
the arithmetic. Zero difference is measured sole-clientness.

Three states, not two — a number is *measured*, a refusal on an engine with no
counter is *looked in a way that cannot see*, a refusal at the open capture is
*not looked yet*. **No boolean anywhere in the field**, which a check asserts on
both engines in both captures.

Eight checks in `tests/test_bench_observed.py`; **eight mutants, all killed** —
including one that found a real gap: a window whose near edge was never read
resolved through no check at all, and now refuses rather than reading zero.
