## "Don't trust any number" was an instruction and it paid

The owner's words: **"run both, don't trust any number!! some are ours and
stale, read vLLM and Ollama documentation regarding this issue first."**

Reading the sources rather than the docs refuted a claim I had already repeated
from a search result — that vLLM subtracts memory other processes hold. It does
not. `v1/worker/utils.py::request_memory` is `ceil(total_memory * util)` with a
hard `free >= requested` precondition, so a neighbour does not shrink vLLM's
budget, it makes vLLM refuse to start. And ollama's silent spill has a named
cause: the pre-flight fit check in `server/sched.go` is guarded by
`len(s.loaded) > 0` — **ollama's own** loaded models — so a foreign process is
invisible to it and llama-server auto-fits into whatever is left.

The instruction also caught two of my own claims. They are listed under
corrections below.

## 0.85 is wrong in kind, not in value — ADR-0039

The waste is large (1,786 MiB on srv1, 7,014 MiB on srv2 at `max_num_seqs 8`)
and it is the least interesting part. Two structural findings sit underneath it:

**A fraction is a statement about a card.** The same 1,792 MiB of KV cache is
`util 0.565` on srv1 and `0.273` on srv2. One number cannot be right for two
cards, and a declaration that must be restated per rig is one that drifts per
rig. Bytes travel.

**Under a fraction, `max_num_seqs` stops being a declared parameter.** The
budget is `total * util - non_kv` and width enters only through activation —
16 tokens out of 131,104 on srv1. So `q15-vllm-s8` and `q15-vllm-s16`, two
entries whose entire difference is their width, **allocated the same KV cache**.
The instrument could not distinguish the two instruments it was built to be.
Under the byte declaration they differ by 1,856 MiB.

`vllm._start`'s `serve.get("gpu_memory_utilization", 0.85)` fallback is
**deleted**. There is no default: an entry declaring neither field is a refusal
naming both, and declaring both is a refusal rather than a precedence rule —
vLLM's own precedence silently discards the fraction, so honouring it would
record a fraction that never applied.

## This bears on #329, and does not settle it

At `0.85` with `max_num_seqs 16`, srv1 gets **131,088** KV tokens against the
**131,072** width 16 requires — a margin of 16 tokens, 0.012% — while srv2 gets
322,304, a margin of 146%. **The two arms of the width-16 cross-rig contrast are
2.46x apart in KV cache from one declared setting**, and no row records it.

#329 asks whether the width-16 gap is hardware or configuration. This does not
answer that. It removes the assumption the phrase "hardware, not configuration"
rested on, which is that the configuration was equal.

## K10 needed repointing, and the guard is what made that visible

Removing `gpu_memory_utilization` from every config made K10 — which watched
exactly that field — fail on its own vacuity guard: *"no config declares any of
('gpu_memory_utilization',), so this check reads nothing and would pass
vacuously"*. It asserted nothing about any value in the tree.

**That is the fifth instance on this lane of a check whose result came from
where it was run rather than what it asserts, and the first that an existing
guard caught rather than a person.** The guard was written for exactly this and
it worked.

Repointed to `kv_cache_memory_bytes` with the owner's sign-off, under ADR-0037's
amendment, then satisfied and its marker removed in the same commit.
Demonstrated red twice: with the origin note stripped, and — the case the rule
is actually about — with the note replaced by a description of what the knob
*does* rather than where its value came from.

## The campaign asks what is possible

Rewritten at the owner's instruction: *"all the possible configs are the
campaigns to check NOT measure — once campaign is done I want to know what is
possible... including MoE models, including same model*n, including n different
models, including switching a model in a co-residency VRAM, including
x*model_1 + y*model_2."*

Six phases in `records/headers/2026-08-22-coresidency-matrix.json`: footprint →
pairs on both sides of the predicted boundary → multiplicity → sets and mixed
multiplicities → transitions → the impossible with its number.

**The design turn is that "ALL combinations" is not enumerable and is bounded by
VRAM.** Phase 0 measures each model's footprint; every later phase is a knapsack
over those measured weights. So phase 0 is 25 cells and about 60 minutes and is
the only phase whose cell list can be written in advance, and the cells beyond
it are declared `unknown` with provenance — inventing a count now would invent
the answer the campaign exists to find. A feasibility cell is a load and a
placement read; a measurement cell is a load and a ramp, and that is the whole
1,782-versus-60 difference.

Throughput is left on the table deliberately, because the contention split is
2.7x between the rigs and is therefore a per-rig campaign of its own that needs
this frontier first to know which configurations are worth timing.

## A fourth defect in the withdrawn plan, and it is why phase 0 exists

Three were on record. The fourth was found while rewriting: **the neighbour's
placement is computed nowhere in the tree.** `_placement(resident, model)`
(`backends/ollama.py:395`) runs for the model under test only, and
`coresidency_arranged` checks an HTTP 200 and a name in `/api/ps` and nothing
else. So the withdrawn header's own first `void_if` — "any cell's neighbour
lands on CPU without the row saying so" — was **unevaluable on all 60 cells**,
not only on the 20 cross-engine ones.

The owner ruled the scope: record **every resident model's** placement, not only
the declared neighbours. That is #335's box 5 and it is now the critical path.
