## The join had to be measured, and it is not the one a port would have written

`nvidia-smi --query-compute-apps=pid,used_memory` gives a pid and a number of
MiB. Turning that into "which model" needs a join, and **the process holding the
card names no model**: vLLM renames its GPU worker with `setproctitle`, so the
pid the driver attributes the memory to has a command line of exactly
`VLLM::EngineCore`. The model is on the **immediate parent**.

Measured on both rigs, 2026-08-22, at the declared serve block of
`srv-full.json`'s `q15-vllm-s8`:

| rig | deployed as | pid | its own command line | parent | driver | card |
|---|---|---|---|---|---|---|
| srv1 | pip `vllm 0.26.0` | 1133972 | `VLLM::EngineCore` | `…/.local/bin/vllm serve Qwen/…` | 3,126 MiB | 3,130 |
| srv2 | docker `v0.26.0` | 364842 | `VLLM::EngineCore` | `/usr/local/bin/vllm serve Qwen/…` | 3,174 MiB | 3,183 |

**Both deployment shapes differ only in the path to the binary**, so one join
covers both — and a reading assembled from the pid's own line would have
returned `None` on every rig and looked exactly like an empty card. This is the
kind of fact that is cheap to measure and expensive to assume.

Also measured, with `qwen2.5-coder:1.5b` co-resident on srv1: the card reads
4,326 MiB, the driver attributes 3,126 to vLLM's worker and 1,196 to a
`llama-server` whose parent is `ollama serve`. **A per-process figure is not the
card** — 4 MiB on srv1 and 9 on srv2 are held and attributed to nobody — so the
two are two fields and are never substituted.

## The decision: the fraction is refused, not computed

ollama reports `size_vram / size` because llama.cpp **spills**. vLLM cannot:
`requested = ceil(total × util)` behind a hard `free >= requested` precondition
means it takes its whole allocation or refuses to start. There is no
denominator.

The owner chose shape 1 of the three the issue stated: **MiB, and `fraction:
null` with its reason on the row.** `1.0` was the tempting one — it is true by
the engine's own contract — and it is the single value a reader would place
beside an ollama `0.068` as though the two were one measurement. That is an
ignored difference resolved silently *on the cell*, which ADR-0038 D4 puts on
the contrast instead. **The frontier now carries two kinds of cell by
construction**, and that is the honest shape of it, not a defect in it.

MiB rather than bytes, one deliberate departure from the literal wording of the
choice: `nvidia-smi` attributes per-process memory to the MiB, so a byte count
would be precision nobody measured, and `_footprint_mib` is already the tree's
unit for a measured footprint. ADR-0039 governs the **declaration**, which is
derived arithmetic and is stated in bytes; this is a **reading**, and a reading
is stated in the unit it was taken in.

  `snapshot` now references the constant instead of carrying its own copy.
- `vllm.residents(host)` — `probe` + `inventory`, so `run.py:568` stops

- `vllm.placements(host)` — one row per process on the card: the model when this

- `vllm.claim` records `resident_placements` and `resident_placements_refused`,
  the same pair `ollama.claim` has carried since #335, and **gates on neither**.
- ADR-0040, and defect 5 closed in §7 of the run contract.

**The sentinel is the part that is easy to skip.** `contract.ssh` returns `None`
for empty stdout, so "no process holds this card" and "the host did not answer"
arrive identical — the same collapse `snapshot` explicitly refuses one reading
over, for `gpu_idle`. The probe conjoins a sentinel to the reading, an unread
card **raises** rather than returning `[]`, and a check holds the two apart.

**One idle reading became a wired one.** §3 of the run contract names three
readings this tree mints and never reads and warns against adding a fourth;
`gpu_compute_apps` was one of them. **Two remain**: `snapshot()["gpu_idle"]` and
the `release()` return `vllm._start` discards.

## Three defects the tree caught before CI did

**Two of them were the repo's own rules, and both were right.**

`test_a_backend_never_names_another_backend[vllm]` refused the change because
the docstrings explaining the decision named the other engine — repeatedly, and
in the file whose own header says it "names no other backend and must not". The
explanation is the reason the rule exists, so the fix was to write it without
the name: *an engine that loads through llama.cpp*, *the other backend's
`residents`*. The rule is checked against the OTHER backends' names, so it
covers a third engine the day its file lands.

`test_every_nested_key_of_checks_has_a_disposition` refused it because
`vllm.claim` grew two keys and no sink said what became of them. Declared in
`LAUNCH_CHECKS_DISPOSITION` and carried by `_claim_fields`, so the launch row
holds them for the same reason the other engine's load row holds its own.

**The third was mine, and it defeats the sentinel with its own separator.** The
probe was `nvidia-smi …; echo <sentinel>`. A missing or failing `nvidia-smi`
writes to stderr and prints nothing on stdout — so the `;` prints the sentinel
anyway, the parser reads a complete reading of an empty card, and the whole
point of the sentinel is gone. It is `&&` now, with a check on the separator
itself. The reading exits 0 when the card holds nothing, so conjunction costs
nothing.

## The sweep reported a false green, and its own accounting caught it

**Mutation sweep 10 of 10 red**, each rejected by the check that names it, with
the failing assertion printed. It did not start there.

The first driver selected its checks with a `-k` keyword expression. That
expression did not match
`test_a_vllm_claim_records_where_everything_on_the_card_sits_and_gates_on_none_of_it`,
so when the mutant that makes the claim **gate** on the placement it was told to
record was applied, the sweep ran nine checks that cannot see it and reported
**GREEN — not rejected**. The mutation was real; the check that rejects it was
not run.

That is the **eighth** instance on this lane of a result that came from *where*
something was run rather than what it asserts, and the second in a row where the
instrument was the sweep rather than the code under it. Session 19's lesson was
that a sweep reporting green is making a claim and needs its own positive
control. This session's correction is one level finer: **it is not enough for
the control to prove that tests ran — it must prove that the check which would
reject this mutant ran.** The driver now selects explicit node ids, asserts the
selection size, and requires each mutant to be rejected **by the named check
that owns it**. "Some test failed" is not evidence that this check works.

Two earlier runs refused to report anything at all — `addopts = "-q"` plus the
driver's own `-q` made pytest print no summary line, so the control read "0
selected" and stopped. That is the control working: a sweep that cannot count
what it ran says nothing rather than green.

## A byte declaration does not buy a launch — #347

Measured while verifying the claim path end to end, and it is not #345's:

srv1, the declared `q15-vllm-s8` serve block verbatim, **no
`gpu_memory_utilization`** exactly as ADR-0039 rule 1 requires. Same command,
same environment, the neighbour the only difference:

| card before launch | outcome |
|---|---|
| 1 MiB, clear | starts, holds **3,126 MiB**; the claim returns `ok: true` |
| 1,196 MiB, a 1.5B resident in the other engine | **refuses at launch** |

```
Free memory on device cuda:0 (4.37/5.61 GiB) on startup is less than desired
GPU memory utilization (0.92, 5.16 GiB).
```

**The first reading of this was not controlled and the second one is.** The
serve block I first ran omitted `FLASHINFER_DISABLE_VERSION_CHECK=1`, so a
second startup failure was possible in the same log and the refusal could not
be attributed to the neighbour alone. Re-run with the declared block verbatim,
the memory `ValueError` is the log's only root cause.

**`--kv-cache-memory-bytes` sizes the KV cache; it does not exempt the launch
from the utilization precondition** — and because ADR-0039 forbids declaring the
fraction, the fraction is vLLM's default **0.92**, the most restrictive value the
entry could have had. The process's real footprint is 3,126 MiB and its
precondition demands 5,160 free: 1.65x what it takes. On a 6,144 MiB card that
leaves room for a neighbour of about 450 MiB, so **a vLLM cell cannot load
second on srv1 at all** under the declaration this project mandates.

Session 18 did not see it because every cross-engine cell it ran declared an
explicit `util 0.30`, and its only srv1 cell was vLLM-first. The failing
combination — byte declaration, small card, vLLM second — had never been run.
Filed as **#347** with three options and an owner decision, because the
campaign's phase 1 is ordered pairs and half of those pairs on srv1 are
otherwise refusals by construction wearing a "does not fit" label.
