## What was already on disk, and what needed a rig

The 2026-08-24 config sweep had captured `/server_info` and a grep of the
startup log for all 104 accepted cells. That was enough to settle the
central question — **is the resolved kernel choice anywhere in
`/server_info`?** — without touching a rig. It is not.

One thing it could not settle. The sweep's grep was
`FlashInfer for top`, which matches srv2's success sentence and nothing on
srv1, so srv1 read as having said nothing about its sampler. Whether that
was silence or a missed shape is not decidable from a record written by the
grep that missed it. So: one launch per rig, baseline flags, whole log kept.
srv1 says a great deal.

```
FlashInfer top-p/top-k sampling unavailable: unsupported compute capability
7.5; falling back. Set VLLM_USE_FLASHINFER_SAMPLER=0 to silence.
```

**The engine names the fallback and its reason.** A one-shape grep over a
two-shape fact turned a stated cause into an absence — #357's defect in
miniature, and `sweep.py`'s pattern is corrected to `FlashInfer top-p`.

## The measurement

One image digest, one model, one identical argument list, both rigs
(`records/evidence/2026-08-24-resolved-config/`).

| field | srv1 (sm_75) | srv2 (sm_86) |
| --- | --- | --- |
| attention backend | `TRITON_ATTN` | `FLASH_ATTN` |
| sampler path | `torch` (fallback) | `flashinfer` |
| linear kernel | `MarlinLinearKernel` | `MarlinLinearKernel` |
| dtype | `torch.float16` | `torch.float16` |
| `serving_resolved_sha256` | `5ac25112…` | `75fd5838…` |
| `serving_build` (before) | `vllm 0.26.0` | `vllm 0.26.0` |

**Why the existing pin could not have caught it.** `/server_info` differs
across the two hosts on five keys: three are card sizing, one is a
per-launch nonce, and the fifth — `quant_config` — differs only in the
**iteration order of a set of 59 layer names**. `vllm_env` adds a sixth of
the same kind. So a digest over that surface moves for four reasons that
are not the instrument and stays still for the one that is. The kernels are
not there to be found at all: `linear_backend` and `moe_backend` read
`auto` on both — the policy that was asked for — and there is no attention
or sampler key.

That is the argument for a second digest rather than a wider first one, and
it is a measurement rather than a design preference.

## What landed

- **`fingerprint.resolved`** — seven declared fields, three read from the
  startup log and four from the engine config, each carrying the verbatim
  engine sentence it was read from. `RESOLVED_READS` declares them,
  `RESOLVED_SIGNATURES` lifts them, `RESOLVED_PATHS` walks the nested config
  (a leaf-name search would have found `dtype` under three parents).
- **The digest is computed only when every declared field was read.** A
  field the engine did not state leaves it null with a reason naming the
  field, so `require_comparable` refuses the row. A digest over
  `{"attention_backend": null}` is a value two servers can share while
  running different kernels — agreement-by-absence, one level in.
- **`serving_resolved_sha256` is in `GROUPS["server"]` and in `KEY`**,
  admitted by qualification rather than by perturbation: it is not a new
  field of the run, it is `serving_build` measured properly, and
  `serving_build`'s own stated justification ("two builds are two
  instruments") had been refuted for the string it holds.
- **`serving_build` names its launcher** — `vllm 0.26.0 via docker`. #329
  landed `launcher_declared` on the launch row; the row is not where the
  gate reads.
- **Asked-vs-resolved is recorded, never repaired** (ADR-0027 D2's shape).
  Comparison happens only where request and outcome share a vocabulary;
  the four fields where they do not each carry a stated reason in
  `RESOLVED_NOT_COMPARED`, because "not compared" and "nobody wrote the
  comparison" are two states and a bare `None` says neither.
- **`tests/test_bench_resolved_config.py`** — twelve cases, including the
  canary: two rows identical in every keyed field, differing only in the
  resolved digest, and the contrast declines them. Its counterpart runs the
  same two rows with one digest and requires them compared, so the canary
  cannot be satisfied by a guard that refuses everything.

## Corrections to #358's body

1. **The dtype claim does not hold for this pair.** The issue states srv1
   `float16` against srv2 `bfloat16`. Both resolve `torch.float16` on the
   1.5B AWQ; the reading came from a different cell. The divergence is the
   attention backend and the sampler.
2. **`/server_info` is not simply unread.** The issue says "nothing calls
   it". `vllm.serving_config` has called it since #326. The gap was that
   what it returns does not contain the resolved kernels, and that one field
   of what it does return reached a row.

## What this costs

Every record written before this field existed carries no value for it, so
a table mixing old rows with new refuses on absence.
`allow_unfingerprinted=True` is how a reader takes an older record
deliberately, and that waiver is ADR-0027 D3's whole purpose. The same
holds for the build string: a docker-launched record written yesterday says
`vllm 0.26.0` and one written today says `vllm 0.26.0 via docker`, so the
two refuse each other. That is a false refusal in the safe direction, and it
is stated rather than smoothed over.

`kv_cache_dtype` is in the digest and is **not** evidence of agreement: the
engine restates it as the policy it was handed (`auto`) and never as the
outcome it reached, on either surface. It refuses two runs that asked
differently and cannot separate two that both asked `auto`. Declared on the
field itself, not left for a reader to infer from a value that looks
resolved.
