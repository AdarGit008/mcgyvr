## Did

Declared the instruments and put a guard at the point of entry. The mechanism
#230 named is real and the fix is small; the interesting part was what the fix
turned up on either side of it.

**The declaration is `tools/instruments.json`, and all three producers read
it.** Five sets: both bundle arms (the floor instrument, in two languages),
`d1r`, `d2`, `d3`. `admit.py`'s hardcoded `EXISTING_TASK_ROOTS` is gone and
reads the same list, which is what makes the id rule below sound rather than
convenient — no pool problem can take an instrument's id, so an instrument id
in a run *is* instrument material.

**A run is classified three ways, because provenance hides in three places.**
The tier it declared, the contract digests it pinned (`tasks_sha256`, which is
`sha256(dumps(contract))` — the same digest the rigs compute), and the
instrument id space its tasks fall in. All three earn their place on the real
corpus:

- `d1`'s digests have been **edited twice**, so a content-only check misses
  every older run of the instrument. The tier rule catches them.
- `python-bundle-2026-08-07` declares **no tier at all** (#227 is why). Its
  digests are exact, so the digest rule names it `bundle-py`.
- `breadth-2026-08-06` declares no tier *and* pins stale `d1` digests. Only
  the id space fires — and five sets share the `t01..t20` shape, so it is
  recognised as instrument material with `primary: null`. A real detection and
  an honest refusal to attribute, which is better than picking one of five.

Strong evidence suppresses the id fallback, so the other 75 runs attribute
cleanly instead of claiming all five sets each.

**The guard at the pin is a stamp, not an exclusion, and that is a deliberate
departure from the issue's first option.** The issue offered either — "refuses
to pin … *equivalently or additionally*, `golden.json` carries the instrument
flag". Excluding would have deleted **9,173 of 12,331 replies** from the
parser's corpus, and ADR-0016 is explicit that the parser must be measured on
the population it actually faces. Dropping three quarters of that population to
protect a *different* consumer curates the parser's corpus down to the shapes
that happen to be safe for fine-tuning — the exact failure ADR-0016 exists to
prevent. The stamp serves both readers. What is not optional is the verdict: a
run that can be classified no way at all is a `PinError`, because an unstamped
run reaches the builder as drawable material.

The stamp is one entry per **run**, not per reply — the property belongs to the
run, and repeating it 8,432 times would bury it. The diff is 604 lines on a
5.7 MB file, and no entry moved.

**The builder refuses stamped material and re-derives the answer itself.** Two
checks on one declaration: the stamp, and a live classification made now. They
are **checked against each other rather than merged**, and disagreement is
fatal. That is the case that matters — a set declared *after* the corpus was
last pinned reads clean in the stamp, and merging would prefer exactly that
stale, permissive answer. Then a final pass over what survived, reading the
classifications rather than the drop counters, so a future edit that reorders
the loop still cannot land contamination.

**A latent bug fell out of it.** `tier = run_meta.get("tier", "d1")` — a run
that never said what it served had its replies rebuilt against the bundle set's
contracts and labelled with the instrument's tier. The default *was* the
instrument. It now refuses rather than guesses.

**What the guard costs, measured rather than feared.** Rebuilt clean, the
training corpus is **608 examples over 150 problems** (571 train / 37 val, 506
TS + 102 PY), all #197 pool material drawn from the 14B and 7B. #189 had **738
examples over 20 problems, every one from an instrument**. So excluding the
instrument did not cost the corpus its useful part — it cost the part that was
never usable, and left something 7.5× wider in problems.
`docs/what-a-tune-may-train-on-2026-08-10.md` states the four candidate sources
and keeps "no usable source yet" available as a finding.

**#189's status, stated precisely, because the issue's framing overshoots.**
The pilot's reported 2×2 is **not** contaminated: it was scored on HumanEval+,
164 Python tasks, and no arm of it ever ran on `d1`/`d2`/`d3` (the graded runs
on those tiers are all base `qwen2.5-coder:3b`). What is destroyed is the
adapter's *future* measurability — 622 `d1` + 116 `d2` examples mean it can
never be scored on the bench ADR-0018 builds, including the Python arm it never
saw, because the arms are paired and #189 measured the transfer itself. So:
UNDECIDED on the benchmark it used (#229), inadmissible on the benchmark that
matters (this issue). Neither is "negative", and the lever remains untested.
Amended into the pilot's summary beside #229's amendment.
