# Session — lane/142 — 2026-08-03

## Did

Wired #114's locator to the only thing that can use it. `decompose()` now takes
`adapters` (defaulting to the gate's own pair, so ownership means one thing on
both sides of the seam) and `_acceptance_for` fills a `type_annotation`
proposal's empty `acceptance` with the checker the target's language adapter
located. A repository declaring none yields a refusal that says so, rather than
a contract the loader would reject three steps later — ADR-0006's "correct
outcome arriving at the correct layer", moved to the layer that can phrase it as
a sentence about the repository.

Three rules, and the second and third are the ones that will look like
omissions later:

- **A proposal that declares its own commands is untouched.** Not overruled, not
  appended to. Appending would let the contract win *and* lose.
- **Only `type_check` is filled in.** `locate_test_command` returns `pytest` for
  any repository with a `tests/` directory — a guess about a runner, not a
  reading of a declaration — and `failing_test_first` needs a *specific* test
  that fails before the change, which no locator can name. Filed as **#146**
  rather than decided in passing; the split is now shipped design and nobody had
  written it down.
- **The refusal sits before dependency resolution**, so one repository-level
  fact cannot arrive disguised as a different complaint per proposal.

**The open question #142 inherited is decided: nothing appends a target,
anywhere.** #114 reasoned that a repository whose `[tool.mypy]` sets no `files`
gets a command needing an argument and that the decomposer, knowing what the
change touched, should supply it. The premise is right; the conclusion does not
follow, on three things measured here rather than assumed:

1. **`tsc --noEmit file.ts` discards `tsconfig.json` entirely.** On a project
   with `strict: true`, the project-wide run reports `TS7006` and exits 2; the
   per-file run over the same file exits **0**. Appending would not narrow the
   check, it would silently replace it with a weaker one that passes — worse
   than no check, because it reports success.
2. **mypy's `exclude` does not apply to a file named on the command line.** On a
   tree excluding `pkg/vendor/`, bare `mypy` exits 0 and `mypy pkg/vendor/bad.py`
   exits 1 on the same file. Appending would check what the repository said to
   skip — inventing scope, the one thing ADR-0006 forbids.
3. **The failure the question feared never reaches a worker.**
   `Acceptance.precondition` runs the list against the *unchanged* tree before
   the first attempt, so bare `mypy` exiting 2 with "Missing target module,
   package, files, or command" is a `PreflightIssue` — an orchestration fault,
   named, no attempt spent. So is a repository carrying a backlog of
   pre-existing type errors, which is the same problem at larger size and which
   no amount of argument-appending would have fixed.

A per-file type check is not a smaller project-wide one; it is a different
check, and in one of the two launch languages it is not expressible at all —
#133's asymmetry arriving in a second place. `python.py`'s docstring, which
promised the decomposer would supply a target, is corrected rather than left to
contradict shipped behaviour.

**Mutation-tested.** Appending `proposal.target` to the located command fails
four tests, including the JS/TS arm and the positive control. The control is
there because "the target is never appended" is an assertion about an absence
and a pipeline that dropped every argument would satisfy it vacuously: a stub
adapter returning `["checker", "--flag"]` proves arguments *can* reach the
contract, so the absence tests are known to be reading something.

`make check` green: 765 passed, lint and mypy clean.

Not tested, deliberately: mypy's and tsc's own behaviour. Both measurements are
recorded here and in `_acceptance_for`, not pinned by a test — `tsc` is not in
the CI image, so pinning only the mypy arm would leave a test that reads as
covering the pair while silently skipping half of it, which is the shape #133
warned about.
