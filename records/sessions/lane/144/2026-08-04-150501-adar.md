## Found

**The mechanism is the half worth keeping, and it is legible in one column.**
CLM-0004's gain came from output rules stopping a small model rambling: 403
completion tokens at `c0` against ~124 at `c2`, and completion tokens dominate
wall time, so that cut *is* the 2.5× speed-up. This run measured them **flat** —
166.8 / 167.3 / 169.4 / 176.6, latency flat to match. The 3b was never rambling
on this task set, so the device the bundle works through had nothing to act on.

That is a better predictor than "which language". It is checkable *before*
running a ladder: measure whether `c0` over-produces. A bundle pays where a
worker over-produces without one, and the language is a proxy for that at best.

**The null needed a positive control, and only one of the two was available.**
#133 already recorded that an all-zero measurement needs one. The one I have
rules out the failure a null is usually made of: the conditions demonstrably
reach and change the model — prompt tokens scale as specified (222/281/608/2180)
and 17, 18 and 20 of 20 tasks returned different outputs under `c1`/`c2`/`c3`
than under `c0`. The system prompt lands; it just does not move acceptance.

The one I could not run is the decisive one. Re-running CLM-0004's *Python*
ladder on this stack would separate "does not transfer to JS/TS" from "does not
reproduce on Ollama and these rigs" — and it cannot be run here, because the
Python **conditions** are vendored but the Python **task set** is not, only its
per-task results. Rebuilding 20 tasks from their ids would be a new instrument
wearing a replication's clothes. So the claim is scoped to the configuration
measured rather than to JavaScript/TypeScript as such, and **#167** carries the
control. This matters beyond #144: if the null is about the stack, CLM-0004 does
not describe the path mcgyvr actually dispatches on, and `python.md`'s standing
is no better than `javascript.md`'s.

**A boolean could not carry the answer.** `Bundle.measured` was False for JS/TS
and about to flip True — the sweep *was* taken on the shipped file, which is all
that flag ever asserted. But True would then read identically for a bundle
measured at +25 pp and one measured at nothing, and "measured" is a word readers
take as endorsement. So `measured` became a derived property meaning provenance
only, and `BundleStanding` carries the outcome: `MEASURED_BENEFIT`,
`MEASURED_NO_EFFECT`, `UNMEASURED`. The third value is not decoration — "measured
and it did nothing" and "never measured" are both un-citable as a gain, for
different reasons, and only one of them is settled.

**Rewriting the marker did not cost the measurement**, which is exactly what
session/1's stripping decision bought: `check_c2_is_the_shipped_bundle` compares
the *stripped* body, so `javascript.md` could stop saying UNMEASURED and start
stating its null result while staying byte-identical to `c2`. The two acceptance
bullets that looked mutually exclusive in session/1 were both satisfied.

**What transferred from CLM-0004's failure list: one of three.** t02 (mutating
the caller's arrays through inner-array aliasing) failed under all four
conditions on both rigs — the same trap both Python models fell into under every
condition. t19 (boolean where a number is expected) and t17/t18 (annotation
form) did **not** transfer; the JS/TS 3b largely handled them. So "some failures
are not a context problem" holds; the specific list does not.

**`MAX_BUNDLE_BYTES` stays one constant, and the reason changed.** #144 asked
whether it should become per-language. A per-language ceiling needs a language
whose curve has a peak; JS/TS measured flat, so there is no JS/TS peak to place
one at — which is *not* the same as JS/TS agreeing that 2 KB is right.
