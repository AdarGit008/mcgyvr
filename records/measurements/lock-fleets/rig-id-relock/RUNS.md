# lock-fleets use `rig-id-relock`

Generated by `records/measurements/lock-fleets/plan.py freeze --use rig-id-relock`; the method and every ruling it applies are in `../README.md`. Nothing above `## Idle minutes` changes once the log holds a row: a run is expandable until its first measurement, and frozen from then on.

## Why this use exists

- srv1's rig id changed under the product rig-id spelling (#483, D1): `mcgyvr.fleet.ids.rig_id` hashes `rig-snapshot.sh`'s own spelling, srv1's snapshot names `rig-3c89f35d…`, and fleet.yaml pins `rig-0f7fc6ae…`, which no rig read prints. Until srv1 is re-locked under the id its snapshot names, every live run is refused.
- A rig id is part of every combination id on its rig and every fleet here places a unit on srv1, so all three fleets re-lock: a-solo, b-small and b-big. Owner, 2026-09-15: "we are using it on our private case (16b -> 35b srv1, 3b + 7b ->80b srv2)".
- srv2's id already reproduces from its snapshot, so its pin must not change (`keep_rig_pins`). b-small's srv2 pair is what live serves, so the dev compose emitted for it must be the live file byte for byte (`compose_must_match_live`).
- The window date is recorded in the log when it runs.
