# Run Request — vLLM × llama.cpp, concurrency n=1,2,4,8

> Filed 2026-08-30. Spec for a serving-throughput sweep that closes the gaps
> found in the 2026-08-24 config sweep and the 2026-08-25 serving sweep.
> Owner rule for rigs: **at will, idle** — free to stop/start services and pull models.

## 1. Objective

Measure aggregate decode throughput for the model ladder at fine concurrency
`n ∈ {1, 2, 4, 8}` on both backends (vLLM, llama.cpp), both rigs, and rank by
the ladder key. Two concrete gaps this run exists to close:

1. The vLLM *tuned* (no-eager + kvfp8) cells only measured `n ∈ {1,8,32,…}` —
   **n=2 and n=4 were skipped**; only the slower `--enforce-eager` baseline
   cells had `n ∈ {1,2,4,8}`.
2. **llama.cpp dense models (3b/4b/7b/14b/16b) have no concurrency curve at
   all** — only the 30b MoE was ramped (raw-postswap-squeeze-concurrency.txt).

## 2. Metric — the key

```
key = agg_tok(n) × total_params
```

- `agg_tok(n)` = aggregate decode tokens/sec across `n` concurrent requests
  (sum over streams), per measured level.
- `total_params` = **full model size, all experts included** (MoE counts its
  total, not active: gpt-oss-20b → 21B, qwen3-coder:30b → 30.5B, 80b → 80B).
- Reported per `n ∈ {1,2,4,8}`, plus `per_stream_tok_s` and `latency_mean/max`
  at each level (the harness already emits these in `levels`).

## 4. Scope & constraints

### Backends

- **vLLM** — `vllm/vllm-openai:v0.26.0` (docker, `--runtime=nvidia --gpus all
  --ipc=host -e FLASHINFER_DISABLE_VERSION_CHECK=1`), AWQ checkpoints.
  - srv1: `--enforce-eager` (Turing CC 7.5 has no FA2/FlashInfer — falls back
    to TRITON; graphs are a no-op, measured).
  - srv2: no-eager + `--kv-cache-dtype fp8` (the tuned "best-config" that hit
    1674 / 2349 / 6445 tok/s in the 08-24 sweep).
- **llama.cpp** — `ghcr.io/ggml-org/llama.cpp:server-cuda-b10481`, GGUF.
  - dense: `-ngl 99` (full GPU).
  - MoE: `-ngl 99 --n-cpu-moe N`, `-t` tuned per (model, rig). **mmap ON** —
    no `--no-mmap`.

### Concurrency grid

`n ∈ {1, 2, 4, 8}` for **every** cell. This is the whole point: the 08-24
tuned grid went 1→8 and lost 2,4.

### mmap-only on MoE — must fit, no thrashing

MoE cells run **mmap only** (default; never `--no-mmap`). A MoE cell is
**refused before launch** if its GGUF size > (available RAM − 2 GB). Concrete
gates:

- srv1 (16 GB): MoE ≤ ~13 GB → only `gpt-oss-20b` (13 GB) and
  `Qwen3-Coder-30B-A3B-IQ3_XXS` (12 GB). `qwen3-coder-30b Q4_K_M` (18.56 GB)
  and the 80b (36 GB) are **excluded from srv1**.
- srv2 (48 GB): all listed MoE fit.

Dense models are unaffected (all ≤ 9 GB) and use mmap (default) regardless.

### Tasks — sample ~10 per n

- Source: `tools/bench/tasks/py/<task>/` (259 dirs; each has `contract.yaml`,
  `accept.py`, `reference.py`).
- Prompt = `contract.yaml` `task` + `interface` + `target_content` (the stub);
  the model completes `solution.py`, acceptance = `accept.py`.
- **Sample one fixed set of 10 tasks, deterministic (seed `20260830`), and use
  the same 10 at every `n`, every model, every rig, both backends** so the
  rows are comparable. ~10 tasks per `n` = 10 tasks × 4 levels, not 40 unique.
- Record the 10 task ids in the cell header so the run is reproducible.

### Download policy

- Pull on need: missing AWQ from HF (`Qwen/…-Instruct-AWQ`, `thewimo/Qwen3-4B-AWQ`)
  or GGUF from Unsloth / tensorblock. Both rigs already hold most GGUF blobs
  (`~/models/dense`, `~/models/moe`, `~/ggufs`).
- **Refuse, don't thrash**: before pulling a MoE GGUF, check it against the
  mmap gate in §4; before launching a vLLM cell, check weights+KV against the
  card (6 GB on srv1 refuses 7B — measured FAIL, record it, don't retry).

## 6. Per-cell procedure

1. Launch backend per §4 (stop the conflicting ollama/llama-moe service first;
   restore after).
2. **Warm up**: 2 calls before recording — srv1 measured a ~1.9× cold-start
   penalty; warm data only.
3. For each `n ∈ {1,2,4,8}`: fire `n` concurrent decode runs over the 10
   tasks, record `agg_tok_s`, `per_stream_tok_s`, `latency_mean_s`,
   `latency_max_s`.
4. Emit one `levels` array per cell (same schema as `max_agg_tok_s` /
   `max_at_n` already used in `records/evidence/2026-08-24-config-sweep/`).
5. Compute `key = agg_tok(n) × total_params` at each n.

Harness entry points (wire the new grid here): `tools/bench/serving/run.py`,
`sweep.py`, `launch.py`; model entries in
`tools/bench/serving/configs/srv-full.json`; rig/unit state in
`configs/hosts.json`. Engine backends: `tools/bench/serving/backends/{vllm,ollama}.py`.

## 8. Success criteria (gaps this closes)

1. vLLM `n=2,4` at the **tuned** config (no-eager + kvfp8), not baseline.
2. First llama.cpp dense concurrency curve (3b/4b/7b/14b/16b) — confirms or
   refutes the "llama.cpp caps ~2×" claim on dense (measured only on MoE 30b).
3. MoE mmap no-thrash verified: each MoE cell's `free -h` available stays
   above the thrash floor; a cell that thrashes is marked FAIL, not averaged.
4. srv1 vLLM 7B FAIL recorded (not retried) — confirms the 6 GB wall.
