**The ascent is a shape, not a loop with a guard.** #24 stopped at a family
boundary and handed over `Exhausted`. What receives it is a tuple of `Plan`,
one per family, built by filtering the catalog's rank-ordered families once
from the contract's floor upward. Every rule #43 states about ordering then
falls out of the shape rather than being enforced: a family appears exactly
once, ranks only increase, and families below the floor are absent rather than
skipped inside the walk. "Each family is entered at most once" is not a check
that could be forgotten — there is nowhere for ping-pong to happen. The whole
climb is also answerable before anything is dispatched, which is the property
#24 gave one family and this extends to the task: which families, which rungs,
how many attempts each, and what stops it, from the config, the pool and the
contract alone.

**Two ceilings, and they bound different things.** `budgets.max_escalations`
already existed, was documented, was generated into the config reference — and
had no consumer anywhere in the repo. It bounds *moves*, which is what its own
doc says, and #43 is the issue whose title it belongs to, so it got wired
rather than reinterpreted. `budgets.max_attempts` is new and bounds *spend*,
which is what #43 asks for by name and is not the same quantity: a rung with
`attempts: 3` spends three with zero escalations.

**Unset means the ladder's own budget, and that is the whole reason the field
could be added honestly.** A number would have been invented — this project has
no measurement for a global attempt ceiling, and #152 is already open about the
last default that was inherited without one. Worse, a defaulted number fights
the other knob: an operator who raises `max_escalations` does not want a
ceiling they never set cutting the climb back. So unset is not "unbounded" — it
is the sum of each reachable rung's `attempts`, which is a real bound, and
`mcgyvr pool` prints it so the claim is checkable rather than asserted.

**A decline charges neither ceiling.** #81's rule needed to survive one level
up: a rung that steps aside spent nothing, so charging it an escalation would
let a ladder of rungs that never ran exhaust the budget. That is what decided
the enforcement mechanism. Pre-trimming the plans to the ceiling would have
been structural and inspectable — and would have charged for declines in
advance, since a trimmed plan cannot know which rungs will step aside. So the
counting happens as it happens, through a `permit` predicate. The test that
holds it sets `max_escalations: 0` and has two rungs decline: the third is
still funded, which is only true if a decline moves the work without being a
climb.

**`route.py` gained a predicate, not a number.** A task-wide ceiling spans
families, so it cannot be computed from one plan; but it also may not live in
`route.py`, because #24's boundary is that nothing there looks past the family
it was asked about. `climb(permit=...)` keeps both true — the module knows a
question was asked and never what the answer means, exactly as it already does
with the attempt function. The refusal is `Exhaustion.WITHHELD`, kept distinct
because a family that was not *allowed* to finish must not read like one that
was tried and could not; every task cut short by a budget would otherwise look
like a ladder that is not up to the work.

**The verification upgrade is unconditional; what the install can do about it
is not.** `verification.policy: gate_only` describes a tool's output through
the gate. The moment work leaves the deterministic family the policy is raised
to require a verifier, whatever the contract declared — leaving it in force
would accept a model's output on a warrant that was never about a model. That
left the apparent conflict with #44 (a keyless install has no verifier and must
still reach acceptance). It is not a conflict once the upgrade is separated
from its satisfaction: `Assurance` records which bar was actually cleared, so
`VERIFIED` is reachable only by a verifier that ran and agreed, and a keyless
install reaches `UNVERIFIED` — accepted on the gate, labelled as exactly that.
E6's epic requires all three configurations to be first-class, so refusing
would have made keyless second-class; what closes the path is that no
acceptance can be *called* verified without one, and that an available verifier
is never skipped. Held by driving the whole policy x family x verifier matrix
and asserting `VERIFIED` is unreachable except from an agreement, rather than
by listing the cases that occurred to me.

**Ordering is structural, and the spy raises.** `judge()` returns on a rejected
gate before the verifier is so much as named, so a gate failure cannot cost
verifier spend however a caller supplied one. The test's verifier raises if it
is ever called: a counter asserted to be zero would pass against a verifier
called and ignored, which is precisely the spend the rule exists to prevent.

**A retry carries what failed and nothing else.** Three exclusions and each has
its own reason, so each is asserted separately: checks that produced no finding
did not fail; observations are findings the gate deliberately did not reject on
(#123), so quoting them would ask for changes never required; and an
environment issue is a tool that was not installed, which is not something the
worker did or can fix. The content rule is in `escalate.py` because it is a
spend rule; `build_prompt(retry=...)` only renders it, and measures it with the
rest of the prompt rather than appending it after the fit check.
