# Session — lane/286 — 2026-08-22 (seventeenth)

**A provenance field that had never once written a value was fixed before its
first campaign, and the fix is a declaration the computation reads rather than
a narrower literal inside it.** Session 16's `.gitignore` fix was confirmed

## The field had never recorded a value, which is the whole reason the timing mattered

`grep -rho '"tree_dirty": *[a-z]*' records/evidence/` returns **nothing**. No
journal row anywhere in the tree carries the field: the D7 rows predate #325
and have no provenance block at all — row 1 of `d7-ramp.jsonl` has seventeen
keys and not one of them is `commit`, `tree_dirty`, `harness_sha256` or
`run_started_at` — and no campaign has run since.

So this is a defect fixed **before** it wrote a single value, not one whose
past readings must now be re-interpreted. No existing evidence is invalidated
and none needs a caveat. It is also why #334 said *before the re-run*: the next
campaign is the first that will carry the field, and it would otherwise have
banked a whole campaign of rows saying nothing.

## The defect belongs to a campaign, not to a run — and #334's own wording over-states it

#334 says every row of every future run would read `true` because the run wrote
its own journal. That is right about a campaign and wrong about the first
invocation, and the distinction is worth having straight because it is the
reason the defect could sit unnoticed.

`provenance()` is called **once**, at the top of a run
(`run.py:202`, `calibrate.py:_stamp`), before `_journal` has appended
anything. A single invocation into an empty directory therefore stamps itself
clean. What makes the field useless is that **a campaign is not one
invocation**. `records/evidence/calibration-2026-08-19/` was written by a
sequence of them spanning four days — `samples.jsonl` 08-19 09:27,
`d7-sleep.aborted-run.jsonl` 16:03, `d7-sleep.jsonl` 19:50,
`d7-survey.json.jsonl` 08-20 00:41, `d7-ramp.jsonl` 04:42, with three `step*.md`
notes written between them — and every invocation after the first sees the
earlier ones as untracked. Add `--resume`, which exists precisely so a killed
campaign is re-entered, and add the lane's own uncommitted edits, and the field
reads `true` for reasons that never touch the harness.

D8 makes this certain rather than likely: `_journal` fsyncs per record on
purpose, so the file is on disk from the first row of the first phase.

## The fix is a declaration, not a narrower literal

The obvious change was to put `HARNESS_SURFACE` into the `git status` call.
What landed instead is `PROVENANCE_SURFACE` — a table beside
`PROVENANCE_DISPOSITION` naming the files each tree-reading provenance field
answers about — with `provenance` reading **both** its `git status` pathspec
and its `product.digest` surface from it, and stating neither itself.

That is what the definition of done's *"the disposition and the computation
cannot drift"* asks for. It buys a second thing the issue did not ask for:
`tree_dirty` and `harness_sha256` are one claim in two halves — *these bytes
ran*, and *a commit names them* — and reading one surface is what stops them
coming to mean different trees. A narrowed declaration now narrows both, which
mutation 4 below is the proof of.

**`commit` is deliberately absent from the table.** `HEAD` is the repository's,
not a surface's; scoping `rev-parse` would be a different claim rather than a
narrower one, and the check asserts it carries no pathspec so nobody adds one
for symmetry.

Untouched, and stated because a provenance change invites the question: no row
gains or loses a key, and `commit`, `commit_unknown_reason`, `config_sha256`,
`argv` and `run_started_at` are byte-for-byte the same computation.

## Six mutations, six red

ADR-0037's price is that a check which cannot be shown to reject is the MARKERS
table again. The sweep was run against the committed form of the file, then
re-run after `ruff format` moved a line, because a sweep against a shape that
did not ship proves nothing.

| | mutation | caught by |
|---|---|---|
| 1 | the whole tree again — the shipped defect, restored verbatim | behaviour |
| 2 | `"tree_dirty": ()` — an empty pathspec, which git reads as everything | behaviour |
| 3 | the pathspec hard-coded beside the table instead of read from it | binding |
| 4 | the digest half reading `HARNESS_SURFACE` instead of the table | binding |
| 5 | `--untracked-files=no` — a file dropped on the rig stops counting | behaviour |
| 6 | `commit` scoped too — `HEAD` stops being the repository's | binding |

Mutation 2 is the one worth keeping in view: an empty tuple is not an obviously
wrong edit, and it silently restores the exact defect being fixed.

The behavioural check builds a real git repository, commits a harness, and
asserts both directions — a journal under `records/` and a survey document
beside it leave `tree_dirty` false **while the unscoped question still reports
them**, and one byte under the declared surface turns it true and moves
`harness_sha256` with it. An untracked file *inside* the surface counts, because
it is code that ran.

Demonstrated on the committed tree, not only in `tmp_path`:

```
clean tree         : False
run wrote a journal: False   <- the fix
unscoped question  : True    <- the defect
```

## Recorded rather than guarded twice

A pathspec that matches nothing exits 0 and prints nothing — verified, not
assumed. So `tree_dirty` alone would read **clean** for a surface entry that had
been deleted or renamed, which is the weaker-pin-that-looks-identical failure
`product.surface_files` already exists to prevent. It does not escape:
`surface_files` raises on a missing declared entry, so `harness_sha256` refuses
the whole stamp before `tree_dirty` can be believed. The docstring says so; no
second guard was added. Naming the hole and where it is already closed is the
point — a second check over the same property is how two things start to
disagree.
