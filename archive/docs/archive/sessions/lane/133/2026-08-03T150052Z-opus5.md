**The survey's result is structural, and it is the part that constrains #110.**
For JavaScript/TypeScript there is no lightweight standalone analogue of
ghostcall, because the capability "does this name resolve?" is not available
outside a type checker. Hallucination Inspector (arXiv:2604.20202) is
Android/Java — its own text: "a custom-built indexer for the Android API level
35". WM-SEMERU's deterministic-AST framework (arXiv:2601.19106) is evaluated on
Python and builds its knowledge base by *runtime introspection of imported
libraries*, which is ghostcall's design and which TypeScript source cannot supply
until it is built. `eslint-plugin-import`'s `import/named`, read at
`01c9eb0`, visits `ImportDeclaration`, `ExportNamedDeclaration` and
`VariableDeclarator` and nothing else, returns early on `importKind === 'type'`,
and is switched off by the plugin's own `typescript` config — on a frame whose
changes are largely type-level it is vacuous by construction. `tsd` judges
assertions the author writes. And oxlint, the fast alternative, documents that
its type-aware rules run in `tsgolint`, which "Builds TypeScript programs using
`typescript-go`", requiring TypeScript 7.0+, a `tsconfig.json`, installed
dependencies and built `.d.ts` files. The lighter tool is the same tool.

So the candidate measured is the TypeScript compiler itself, through
`ts.createProgram` → `getSemanticDiagnostics`, with the verdict read off the
diagnostic code. `tools/reach/count3_jsts.py`, three arms, 27 changes, 81 rows.

**The number is zero, in every arm, and the work that makes that a result rather
than a shrug is `--control`.** Zero existence verdicts on added lines against 338
call expressions, 360 property accesses and 2576 identifiers; zero whole-file
too, against 2952 / 3110 / 22724. Because every cell was zero — unlike
`count3.py`, whose Python arm had flags off the added lines to characterise — a
resolver that had silently failed to build a program would have produced exactly
the same table. `--control` writes a file of references that certainly do not
exist into the frame at its pinned commit, measures it through the same driver
and deletes it; all three arms flag all four of 2304, 2305, 2339 and 2551, and
none flags the correct `produce(...)` call sitting in the same file.

**What the arms separate is cost, and it is not what #133 predicted — which was
the point of testing it.** #133 expected the Python failure mode to transfer or
not: ghostcall's every false positive was platform-conditional code correct on
the platform it guards, because it resolves against a live interpreter. A
type-graph resolver has no running platform to be wrong about, and produced no
platform-conditional flag anywhere. It acquires two different failure modes, both
environmental rather than about authorship. With the frame's own `node_modules`
and its own `typescript` 5.0.2 the run is completely clean — nothing in `src/` at
any of the 27 commits. Staging *our* `typescript` 5.9.3 against the same
installed tree turns that 0 into **153 diagnostics on code that shipped**, all
type-compatibility (2416, 2322), none an existence verdict. Removing
`node_modules` turns it into **146 flags at 21 distinct sites, every one of them
2580 `Cannot find name 'process'`** on correctly-guarded code. Neither set lands
on a line these 27 changes added, which is a fact about which lines this corpus
contains and not a property of the resolver — recorded as such rather than
banked.

The staged resolver is pinned by the sha512 of its published tarball and verified
in the container before it is unpacked, failing closed on a mismatch — ADR-0011's
rule applied to a resolver that is staged rather than installed. The
existence/environment classification table is not taken from documentation: the
driver extracts each code's message template from `lib/typescript.js` of the
resolver that produced the verdicts, so the classification and the measurement
come from the same bytes. `diagnostic-codes.json` says which half of that table
is TypeScript's and which is this repository's assignment.

**One finding about the repository rather than the resolver, for #114 and #132:**
immer declares **no type-check command** in `package.json` at any of the 27
commits, while pinning `typescript ^5.0.2` at all of them. A rung that delegated
to the target's *declared* type-checker under ADR-0006 would have had nothing to
run on this frame, even though the repository ships both a compiler and a
`tsconfig.json` for one to use.
