**The design decision the acceptance turns on is where the slot is held, not how
it is counted.** Capacity is keyed by **source** — a ladder of four rungs on one
machine is four names for one card — and acquired around **one dispatch**, not
around a task. So "a task escalating across sources does not leak or
double-count" is not a rule the code follows; it is a thing the code cannot do,
because a task never owns a slot. There is no per-task ledger to get wrong. The
slot is returned however the dispatch leaves, so a backend that times out does
not cost the source capacity for the rest of the run.

`run_batch(jobs, capacity)` runs a batch under that bound. It hands each job the
capacity rather than letting jobs close over one, because a job that dispatches
without holding a slot silently breaks the only guarantee the module offers and
the signature is the one place that can put the thing into its hand. Results come
back in **input order** — ordering by completion would make a batch reproducible
only on a quiet machine — and a job that raises becomes a named failure beside
its neighbours' results.

**Two things it refuses rather than does.** A nested hold on a source the calling
thread already holds raises: at the default `max_parallel: 1` that would block
forever against itself, with no output and no traceback, which is the worst
failure this module could have. And an endpoint whose declared `max_parallel`
disagrees with the bound being enforced raises, because two answers to one
question means one config is stale.

**Measured on the executor**, since there is no live backend on this machine: 12
jobs of 50 ms across sources of capacity 3 and 2 took **0.205 s against 0.604 s
serial — 2.94x**, floor 0.150 s set by the two-slot source. That measures *this
module* and is stated as such; it is not a throughput claim about a backend,
which is CON-01's (three models on one card, 23.6 s against ~44 s serial) and
CON-04's, both taken on real hardware. The test asserting it leaves a wide margin
because a flaky timing test is worse than none, and the non-vacuity is carried by
structural assertions instead: an **independent** observer counts arrivals and
departures from inside the held block, and every ceiling test asserts the ceiling
was *reached* as well as never exceeded.

**Mutation-tested, both halves.** Removing the semaphore acquire fails four
tests. Acquiring but releasing before the request — counted, not held — fails the
two that watch from inside the transport, which are the only ones that could tell
the difference.

next: #24.

**#24 is the natural successor and is what `run_batch`'s job shape was left open
for.** The unit of a batch here is deliberately a *job*, not a contract:
executing a contract means choosing a rung, assembling a prompt, parsing a reply
and escalating on failure, and supplying a contract loop in #23 would have been
inventing the escalation policy #24 exists to decide. When #24 lands, its
per-contract executor is the job, and nothing here should need to change.

**Two things #24 will meet immediately.** First, `dispatch(capacity=None)` is
unbounded by default — right for a single request, wrong for a batch — so the
escalation loop must thread a capacity through every rung it tries, and the
per-dispatch acquisition only pays off if it does. Second, `Usage.waited_seconds`
is the signal that a declared capacity is throttling a batch; #24 is the first
caller in a position to act on it, and nothing yet reads it.

Not in scope and deliberately untouched: the sleep/wake and model-swap
controllers (#70, v2, and the issue says so), and `Capacity` growing a notion of
cost or fairness — every slot on a source is currently interchangeable, and a
priority scheme would need a policy nobody has written down.
