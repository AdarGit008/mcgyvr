  `(tier, task)`, which the issue floated and which is the opposite error: the
  same contract served by two tiers of one language would get two budgets. The

  entry `golden.json` happened to list first. The survivor's `model` steers the
  round-robin, so without this the output depended on corpus entry order.
  `dropped` is serialised sorted.

## What the measurement said, against the issue's prediction

Built against the real corpus, both ways. The two defects are not equally live:

- **The shared cap is latent.** 147 problems, 195 arms, 16 arms at the cap —
  and *no* problem has both a capped arm and a Python arm. The Python arms are
  tiny (max 5 replies) because only one 7B Python sweep exists, while the capped
  arms are the d1 twenty with thousands of draws. Old and new builds emit the
  identical 1058/101. The fix is correct and becomes load-bearing the moment
  Python volume grows; today it changes only the reported `arms` count
  (147 → 195).
- **The split was actively leaking.** Under the old per-reply rule, **18 of 48
  paired problems straddled train and val** — 37.5%, well above the ~18% the
  issue estimated from 2 × 0.1 × 0.9, because a problem with many replies has
  many chances to catch a val bucket. Val moves 123 → 101 under the problem
  split.

Both invariants were verified by reverting each fix in turn and confirming the
matching test fails. A test that passes against the buggy code proves nothing.
