# Project Engineering Handbook

## 1. Project overview

This codebase implements a two-tier AI orchestration platform. An API-tier
orchestrator decomposes engineering work into small, tightly-scoped task
contracts and dispatches them to local worker models running on constrained
hardware. Worker output is verified by an acceptance pipeline before being
merged. The platform's economics depend on workers producing accepted,
production-quality output on the first pass: every remediation round costs
latency and every escalation to the API tier costs money. Your role as a
worker is the innermost loop of this system — correctness and contract
compliance are worth more than cleverness.

## 2. Repository layout and module conventions

- `src/orchestrator/` — task routing, tier-cascade logic, escalation rules.
  Workers never import from here.
- `src/workers/` — worker-side client wrappers and contract handling.
- `src/instrumentation/` — benchmarking and telemetry harnesses. All
  measurement code is dependency-free so it runs in any environment.
- `config/` — model and proxy profiles. Configuration is data, not code:
  never hard-code a model name, port, or path where a config key exists.
- `data/` — benchmark results and datasets. Append-only; never rewrite a
  results file in place.
- Tests mirror source paths: `test/<module>.test.ts`. A module with no test
  file is considered untested regardless of coverage elsewhere.
- One module = one responsibility. If a helper is used by two modules it
  moves to a shared module rather than being imported across siblings.
- ESM only. Every relative import carries its file extension; there is no
  CommonJS `require` anywhere in the tree.

## 3. Naming conventions

- Functions and variables: `camelCase`, verbs for functions (`parseRow`,
  not `rowParser`), nouns for values.
- Classes, interfaces and type aliases: `PascalCase`, nouns (`TaskContract`,
  `WorkerProfile`). Interfaces are not prefixed with `I`.
- Constants: `UPPER_SNAKE` at module top, after imports, before any code.
- Private helpers: not exported. `#private` class fields are preferred over a
  leading underscore, which carries no enforcement.
- Boolean names read as predicates: `isValid`, `hasCapacity`, `shouldRetry`.
- Avoid abbreviations except: `cfg`, `ctx`, `msg`, `req`, `res`, `idx`.
- File names match their primary export: `ollamaClient.ts` exports
  `OllamaClient`.

## 4. Error-handling policy

- Validate arguments at public boundaries; internal helpers may assume
  validated input.
- `TypeError` for wrong types, `RangeError` for values outside a bound, and
  plain `Error` for everything else. Custom error subclasses are defined only
  in the orchestrator layer, never in worker output.
- Error messages state what was wrong and what was expected, in one short
  sentence, without the word "error": `"n must be positive, got -3"`.
- Never catch an exception you cannot handle meaningfully. An empty `catch`
  block is a defect; re-throwing unchanged is preferred over wrapping when no
  context is added.
- A floating promise — one created and never awaited or `.catch`ed — is a
  defect even when the operation cannot fail.
- Timeouts and resource limits are enforced by the harness, not by worker
  code — do not add signal handlers, `AbortController` plumbing or watchdog
  timers.

## 5. Testing philosophy

- Every acceptance test must be runnable in isolation with no repo-wide
  fixtures: `node accept.mjs` from a temp directory must be sufficient.
- Tests assert on behavior, not implementation: call the public interface,
  never reach into private fields.
- Boundary values are tested explicitly: empty, single element, exact
  capacity, one past capacity.
- Deterministic by construction: no wall-clock time, no `Math.random` without
  a fixed seed, no network, no environment variables.
- A test that sometimes passes is treated as a failing test.

## 6. Performance guidance

- Workers target correctness first; optimize only when the contract states a
  bound. When it does, honor it precisely (e.g. "must handle n=90" means the
  naive exponential solution is wrong even though it is correct).
- Prefer O(n) single-pass solutions where natural, but never at the cost of
  readability for the input sizes stated in the contract.
- Generators over materialized arrays when the consumer iterates once; arrays
  when the contract's interface declares an array.
- String building in loops uses `parts.join("")`, not repeated `+=`.
- `Map` and `Set` lookups over repeated linear scans when the same collection
  is probed more than twice. Prefer `Map` to a plain object when keys are not
  known statically.

## 7. Security and safety rules

- Worker code never executes its input: no `eval`, no `new Function`, no
  dynamic `import()` of a path derived from arguments, no `child_process`.
- No filesystem access outside paths named in the contract; no network
  access ever.
- Regexes on untrusted input must not be susceptible to catastrophic
  backtracking (no nested unbounded quantifiers over the same character
  class).
- Never assign to a key derived from input without checking it: `__proto__`,
  `constructor` and `prototype` reached through a computed property are how
  prototype pollution enters a codebase.
- Secrets never appear in code, comments, JSDoc, or test data — not even as
  placeholders shaped like real credentials.

## 8. Review checklist applied to worker output

Reviewers (human or model) check, in order:
1. Interface fidelity — names, signatures, return types exactly as declared.
2. Contract constraints — every CONSTRAINTS bullet is satisfied.
3. Scope — nothing outside the contract's target is touched; no unrequested
   features.
4. Acceptance — the stated acceptance command passes.
5. Edge cases — the checklist above was visibly considered.
6. Style — standards section violations are remediation-level, not
   rejection-level, unless the contract lists them as constraints.
Output failing items 1–4 is rejected outright; the task is re-dispatched
with the failure output attached.

## 9. Git and change conventions

- Commit messages: `type(scope): summary` — types are feat, fix, bench,
  docs, chore, refactor. Scope is the module or issue number.
- One logical change per commit; benchmark data lands in the same commit as
  the code that produced it.
- Branches follow the lane model: `lane/N` anchored to an issue, session
  records under `records/sessions/lane/N/`, and no direct pushes to main.
- CHANGELOG entries are written when a change is user-visible or alters a
  measured result; internal refactors are not logged.

## 10. Documentation rules

- Docs state facts that are stable; volatile facts (model scores, VRAM
  numbers) live in `data/` and are referenced, not copied.
- Every design document opens with the issue number it serves.
- "Derived, not stored": status documents describe how to compute current
  state rather than snapshotting it.
